## 1. Fixture-Level Transaction Wrapping (Recommended Pattern)

### How It Works

1. **Begin a transaction** at the start of each test (e.g., in a pytest fixture).  
2. **Run all test code** (setup, actions, and assertions) within that same transaction scope.  
3. **Rollback the transaction** at the end of the test, so any changes are reverted automatically.

### Advantages

- Keeps each test fully isolated in its own transaction.  
- No need for nested transactions (i.e., no reliance on savepoints).  
- Automatically cleans up state changes, removing the need for explicit test cleanup logic.

### High-Level Example

```python
import pytest
from sqlalchemy.ext.asyncio import AsyncSession

@pytest.fixture
async def db_session(session_factory):
    """Fixture that begins a transaction and rolls it back after each test."""
    async with session_factory.get_session() as session:
        # Begin the outer transaction.
        async with session.begin():
            yield session
            # As soon as we exit this scope, the transaction is rolled back
            # if using session.begin() as a context manager or you can do it manually if needed.
            # session.rollback() would happen automatically on context exit if an exception occurred.
```

Then, in your test:

```python
@pytest.mark.asyncio
async def test_session_rollback(db_session):
    # db_session is already in a transaction
    await db_session.execute("INSERT INTO test_rollback (value) VALUES ('initial1')")
    # You can do rollback testing within this transaction if you like;
    # ultimately, upon fixture tear-down, the entire transaction is rolled back.
```

**Key note**: In a typical “transaction-per-test” pattern, you might do the state verification *within the same transaction*. If you want to verify from a “fresh transaction” viewpoint, you could open a separate, *independent* session to see the committed state. But in pure test-rollback patterns, it’s quite common to just rely on ephemeral data and trust that once you exit, everything is discarded.

## 2. Use of Separate Sessions for Setup/Verification

If you absolutely need to test partial commits, rollbacks, and so on, you might consider:

1. **Session A** for initial setup and commit.  
2. **Session B** for performing test operations that you want to rollback.  
3. **Session C** for verifying from a *fresh transaction* that those changes were (or weren’t) committed.

This can get tricky, but it simulates real-world usage more closely—especially if you are testing transaction boundaries and concurrency.

**Sketch**:

```python
@pytest.mark.asyncio
async def test_session_rollback(session_factory, test_case):
    # Session A: do setup and commit
    async with session_factory.get_session() as session_a:
        async with session_a.begin():
            await test_case._setup_initial_state(session_a)
        # Once we exit the 'begin()' context, everything is committed.

    # Session B: do test operations and rollback
    async with session_factory.get_session() as session_b:
        async with session_b.begin():
            await test_case._perform_test_operations(session_b)
            # Force a rollback
            await session_b.rollback()

    # Session C: verify the state from a fresh perspective
    async with session_factory.get_session() as session_c:
        await test_case._verify_rollback_state(session_c)
```

**Pros**:
- You’re less likely to get tangled with nested transaction scopes.  
- More closely matches “real usage” if you’re testing concurrency or transaction boundaries.

**Cons**:
- Requires more boilerplate (setup session, test session, verification session).  
- Have to handle or clarify session lifecycles carefully.

---

## 3. Avoid Nested Transactions / Savepoints with `asyncpg`

As you discovered, `asyncpg` is notorious for partial support of nested transactions. In many cases, `SAVEPOINT` usage can raise a `NoActiveSQLTransactionError` if the driver or the connection state machine gets confused. If your use case absolutely requires nested transactions, consider:

- **Switching to psycopg** (psycopg3 supports async usage, though it is still relatively new).  
- **Handling savepoints manually** with raw SQL statements (`SAVEPOINT`, `ROLLBACK TO SAVEPOINT`) at the connection level, though you must manage the connection carefully.

However, if the goal is simply to test rollbacks, a simpler per-test or per-session transaction pattern is usually more than enough.

---

## 4. Using a Test Database or Ephemeral Schema

An alternative approach (often used in large test suites):

1. **Create a dedicated test database** (or ephemeral schema) before tests run.  
2. **Run all tests** with normal commit/rollback as needed.  
3. **Drop or discard** that test DB/schema at the end of the test run.

This means you don’t necessarily rely on rollbacks to clean your data after each test. Instead, you can run the tests “for real” with normal commits, and then just blow away the entire schema at the end. This is especially helpful when dealing with complicated multi-transaction tests or if you want to see the “actual” DB state between tests:

**Pros**:
- No weirdness with nested or partial transaction states.  
- Each test can fully commit or rollback as you like.  
- The entire DB is ephemeral—once the test runner ends, the DB is discarded.

**Cons**:
- Possibly slower to re-create a DB for each test run.  
- Harder to keep tests fully isolated if you rely on persistent state across tests.

---

## 5. Verifying State After Rollback

### Common Patterns

1. **In the same transaction**: If you do a rollback inside your test transaction, you’re typically verifying the state with the same session. Keep in mind that once you call `rollback()`, you might need to re-begin a new transaction or recheck the session state.  
2. **From a fresh session**: After the rollback, open a separate session in autocommit or a new transaction to confirm that the changes truly aren’t present. This can help avoid confusion with session caching or transaction isolation quirks.

```python
await session.rollback()

# Optionally re-begin a new transaction if needed
async with session.begin():
    # re-verify state
```

Or simply:

```python
# After the rollback, open a new session for verification
async with session_factory.get_session() as verify_session:
    await test_case._verify_rollback_state(verify_session)
```

## 6. Checking for asyncpg-Specific Issues

You asked whether a different driver would help. If you rely heavily on nested transactions or other advanced transaction features, `psycopg` (especially the newer psycopg3) often has more robust support. That said, many teams do use `asyncpg` successfully. The main watchout is that nested transaction or savepoint usage is more brittle than standard single-transaction usage.

## 7. Summary & Best-Practice Recommendations

1. **Use Fixture-Level Transaction Wrapping**: By far the simplest way to keep tests isolated, especially if you just need to “simulate changes then discard them.”  
2. **Limit or Avoid Nested Transactions**: They add complexity and can cause driver-level issues. If you must test partial commits, consider using separate sessions or a fresh test DB.  
3. **Verify State in a Fresh Session**: After rolling back, confirm changes are gone from a new connection/transaction. This ensures no caching or leftover state from the original session.  
4. **Consider Alternative Drivers**: If nested transactions or unusual transaction behaviors are essential, you may find `psycopg` or `psycopg3` more straightforward.  
5. **Ephemeral Test Database**: If your test suite is large and you want “full realism” (i.e., actually committing, rolling back, etc.), spinning up a short-lived test DB (or a Dockerized container) and then discarding it after the suite is often the cleanest approach.

- **Stick to the simplest pattern** (per-test transaction rollbacks) unless you specifically need to test partial commits or concurrency edge-cases.  
- **Be mindful of session scoping**: mixing “manual” `begin()` calls with context-manager-based commits or rollbacks can easily cause confusion in SQLAlchemy’s state machine.  
- **Test Cleanup** becomes trivial if you rely on either transaction rollback or ephemeral DB approaches, rather than manual table truncation.

Below is a **working example** of how you can structure your async tests with **SQLAlchemy** and **asyncpg** so that:

1. Each test runs within its own transaction.  
2. That transaction is rolled back on errors (or at test teardown).  
3. You don’t get unwanted implicit commits when the session is closed.  

The key ideas are:

- **Use a single database connection** per test and explicitly begin a transaction on that connection.  
- **Bind your `AsyncSession` to that connection** so that all operations share the same transaction context.  
- **Rollback or commit** at the end of the test (or upon error).  
- Make sure **implicit commits** are avoided (e.g., by not closing a session that still has an active transaction, or by not creating nested transactions when your driver does not support them).

---

## 1. Create an Async Engine Fixture

Create an async engine once (per session or module) and then dispose of it when done. This ensures all tests can reuse the same engine without repeatedly opening new connections:

```python
# conftest.py or tests/conftest.py

import pytest
from sqlalchemy.ext.asyncio import create_async_engine

@pytest.fixture(scope="session")
def db_url() -> str:
    """
    Return your test database URL string.
    Example:
        "postgresql+asyncpg://test_user:test_password@localhost/test_db"
    """
    return "postgresql+asyncpg://user:password@localhost/test_db"

@pytest.fixture(scope="session")
async def async_engine(db_url):
    engine = create_async_engine(db_url, future=True, echo=False)
    yield engine
    await engine.dispose()
```

- `scope="session"` ensures the engine is created once for the entire test session.  
- `await engine.dispose()` properly closes all connections at the end.

---

## 2. Create a “Per-Test” Transaction Fixture

We want each test to run inside a fresh transaction, which will be rolled back at the end. By doing so, the database is restored to the initial state before each test.  

```python
# conftest.py or tests/conftest.py

import pytest
from sqlalchemy.ext.asyncio import AsyncSession, AsyncConnection
from sqlalchemy.orm import sessionmaker
from sqlalchemy.sql import text

@pytest.fixture
async def db_connection(async_engine) -> AsyncConnection:
    """
    Creates a single Connection for the test and starts a transaction.
    Rolls it back at the end of the test.
    """
    async with async_engine.connect() as conn:
        # Start a transaction
        trans = await conn.begin()

        try:
            yield conn
        finally:
            # Rollback the transaction after the test
            await trans.rollback()


@pytest.fixture
async def async_session(db_connection: AsyncConnection) -> AsyncSession:
    """
    Binds an AsyncSession to the same Connection so that
    all operations share the same transaction context.
    """
    async_session_maker = sessionmaker(
        bind=db_connection,
        expire_on_commit=False,
        class_=AsyncSession,
        autoflush=False,
        autocommit=False,
    )
    async with async_session_maker() as session:
        yield session
        # No need to explicitly commit or rollback here;
        # the connection-level transaction fixture handles rollback.
```

### Why This Works

- We acquire a **single connection** (`db_connection`) and **explicitly begin()** a transaction on it.  
- We yield that connection to the test, then **rollback** in the `finally:` block.  
- The `async_session` fixture uses that **already-open** connection, so anything done via `session.execute(...)` or the ORM is part of the **same transaction**.  
- When the test ends (or fails), the rollback in `db_connection` fixture ensures **no changes persist**.

## 3. Example Test That Verifies Rollback

Below is an example test case that:

1. Creates a table.  
2. Inserts some rows (verifies count).  
3. Intentionally raises an exception to force a rollback.  
4. Verifies that changes made inside the transaction were indeed rolled back.  
5. Cleans up the table.

```python
# test_rollback.py

import pytest
from sqlalchemy.sql import text

@pytest.mark.asyncio
async def test_session_rollback(async_session):
    """
    Demonstrates that changes made within a transaction are rolled back
    when an error is raised (or at test teardown).
    """

    # 1) Create table
    await async_session.execute(text("""
        CREATE TABLE IF NOT EXISTS test_rollback (
            id SERIAL PRIMARY KEY,
            value TEXT
        )
    """))

    # 2) Insert some initial data
    await async_session.execute(text("""
        INSERT INTO test_rollback (value) VALUES ('initial1'), ('initial2');
    """))
    # Flush so we can read back in the same transaction
    await async_session.flush()

    # 3) Verify initial data count
    result = await async_session.execute(text("SELECT COUNT(*) FROM test_rollback"))
    count = result.scalar()
    assert count == 2, f"Expected 2 rows initially, but found {count}"

    # 4) Insert more rows in the same transaction
    await async_session.execute(text("""
        INSERT INTO test_rollback (value) VALUES ('test1'), ('test2');
    """))
    await async_session.flush()

    # Now 4 total rows should exist
    result = await async_session.execute(text("SELECT COUNT(*) FROM test_rollback"))
    count = result.scalar()
    assert count == 4, f"Expected 4 rows after insert, but found {count}"

    # 5) Force an error to cause rollback
    raise Exception("Simulated error to trigger rollback")


@pytest.mark.asyncio
async def test_verify_rollback_effect(async_session):
    """
    Verifies that data inserted in the previous test was indeed rolled back,
    leaving no leftover data.
    """
    result = await async_session.execute(text("SELECT COUNT(*) FROM test_rollback"))
    count = result.scalar()
    # Should be 0 if last test table creation/inserts were rolled back
    # Or no table at all if it was never committed
    # If the table was created but not dropped, you could find 0 rows.
    # If the table was also rolled back entirely, you might see an error here.
    assert count == 0, f"Expected 0 rows after rollback from previous test, but found {count}"

    # Clean up table if it exists
    await async_session.execute(text("DROP TABLE IF EXISTS test_rollback"))
```

### Notes

- The first test `test_session_rollback` will raise an exception partway through, meaning the transaction will be rolled back in the `db_connection` fixture.  
- The second test `test_verify_rollback_effect` shows that the previously inserted rows do **not** persist because of the rollback.  
- Depending on your requirements, you may or may not want to create/drop the table in each test. Some teams prefer running migrations once at the test session start. Others prefer on-the-fly creation and dropping for more isolated tests.

## 4. Common Pitfalls and Gotchas

1. **Using Multiple Sessions or Connections**  
   If you create a new session/connection for verification, you might see “committed” data if your main transaction was implicitly committed somewhere. Always ensure you’re checking with the **same connection** or the same transaction context if you truly want to see uncommitted data.

2. **Implicit Commits on Session Close**  
   If you simply do `async with async_sessionmaker() as session:` without an explicit `begin()`, SQLAlchemy may `BEGIN` a transaction and `COMMIT` when exiting the `with` block. The fixture approach shown above avoids that by controlling the transaction at the **connection** level.

3. **Savepoints**  
   `asyncpg` has limitations around nested transactions and savepoints compared to `psycopg2`. If you truly need nested transactions, you may have to ensure your `postgresql` server and driver support it properly. Often you can do simpler patterns with a single transaction per test.

4. **Isolation Levels**  
   Make sure your database defaults (e.g., `READ COMMITTED`) aren’t interfering with your test logic. Typically, standard isolation levels are fine, but in rare cases or more complex concurrency tests, you might need to adjust.

5. **Creating/Dropping Tables**  
   Frequent creation and dropping of tables can be slow for large test suites. You might prefer to run migrations once before your tests start, then use `TRUNCATE` for each table in a transaction. Or (as in the example), just create and drop as needed for small test scenarios.
